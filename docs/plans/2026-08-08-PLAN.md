# Interactive First-Person Helicopter Insertion

## Outcome

Build the offline `OperationsDemo` campaign opening as an interactive Timeline sequence. On a fresh campaign, the player begins seated in a helicopter, remains in the normal first-person camera, and can look around within configurable limits. Movement, weapons, traversal, stance changes, and interaction remain unavailable until touchdown. The landing transitions into normal gameplay without a scene load or camera cut.

Version one uses a graybox helicopter, plays once per local campaign profile, and has no player-facing skip control.

## Acceptance Criteria

- A profile without a completion flag enters the helicopter sequence automatically when `OperationsDemo` loads.
- The player follows the animated seat without positional drift and can look around without gaining control of movement or weapons.
- Look is bounded in seat-local yaw and pitch; helicopter turns and banking do not change or invalidate those bounds.
- Pause uses the existing Operations UI. Pausing freezes the Timeline, releases the cursor, and disables gameplay input; resuming continues the same Timeline time and restores passenger look.
- The touchdown handoff places the player at a stable world-space marker, restores collision and every gameplay control exactly once, reveals the weapon, and emits `MissionStarted` exactly once.
- A completed profile, or a reload after successful touchdown, starts directly at the drop marker without briefly showing or playing the insertion.
- Invalid setup or an interrupted director recovers to a playable state and logs an actionable error; no failure path leaves the player parented, invisible, input-locked, or without collision.
- No third-party KINEMATION or CAS source file is modified.

## Existing Project Integration

- `Assets/Scenes/OperationsDemo.unity` contains the active offline player instance from `Assets/Integrations/KINEMATION/CAS_Player_Example_FPS_Tactical.prefab`.
- That project-owned prefab currently uses the vendor `CAS_Demo.Scripts.FPS.FPSExampleController`. Add a project-owned subclass under `Assets/FPSProject/Player/` and replace the component on the project-owned prefab while preserving all serialized controller values. Do not add insertion behavior directly to files under `Assets/CAS Demo/` or `Assets/KINEMATION/`.
- The active rig combines CAS locomotion with a Tactical weapon presentation. Passenger mode must gate both the CAS input/motor path and any Tactical firing/presentation path; disabling movement alone is insufficient.
- `FirstPersonProject.UI.ProjectSapphireBridge` already owns Escape polling, `Time.timeScale`, `PlayerInput` activation, and cursor capture. Keep it as the sole pause/cursor authority. The insertion code should request normal gameplay cursor capture when it starts or resumes, but should not implement a second pause action.
- There is currently no campaign or checkpoint service. Version one therefore owns only a namespaced `PlayerPrefs` completion flag. Future checkpoint integration can consume the same public completion API without being implied by this milestone.
- Timeline `1.8.12` and Input System `1.19.0` are already installed. Do not add Cinemachine or Unity Splines for this sequence.

## Scope

- A project-owned FPS controller subclass with `Gameplay` and `ScriptedPassenger` control modes.
- A single-scene insertion director, persistence helper, graybox helicopter prefab, Timeline asset, audio/animation bindings, touchdown signal, and drop marker.

## Proposed Runtime Components

Use project-owned scripts under `Assets/FPSProject/Campaign/Insertion/`, with tests in a sibling `Tests` folder.

### `PlayerControlMode`

```csharp
public enum PlayerControlMode
{
    Gameplay,
    ScriptedPassenger
}
```

Keep the enum independent of the helicopter director so other scripted sequences can reuse the same input lock later. Only the controller changes its own mode; external systems call explicit entry/exit methods rather than setting the enum field directly.

### `ProjectFPSController : FPSExampleController`

Expose read-only `ControlMode` plus idempotent methods similar to:

```csharp
public bool EnterScriptedPassenger(Transform seat, PassengerLookSettings lookSettings);
public void ExitScriptedPassenger(Quaternion gameplayFacing);
public void ForceGameplayRecovery();
```

Passenger mode responsibilities:

- Validate the seat reference before changing state.
- Keep the root `PlayerInput` component enabled so `Look` messages continue. The Operations pause UI may temporarily deactivate and reactivate it while paused.
- Accept `Look` only. Reject `Move`, `Lean`, `Aim`, `TogglePerspective`, `Jump`, `ChangeItem`, `Crouch`, `ToggleWalk`, `Sprint`, `UseItem`, `Interact`, `ChangeShoulder`, `Reload`, `ChangeFiremode`, `DigitSelected`, and `AlternativeAim` before they mutate controller or weapon state.
- Treat the callback list as an explicit allowlist: any newly added action must default to blocked in passenger mode and be added to the passenger-mode tests before it is permitted.
- Gate the controller's per-frame movement simulation as well as callbacks. The base controller runs movement and gravity from `Update()`, so callback checks alone do not prevent cached input or residual velocity from moving the player.
- On entry, clear move/look deltas, sprint, jump requests, lean, aim, current firing, and residual horizontal/vertical velocity. Normalize crouch before disabling the motor so capsule dimensions are restored.
- Disable the root `CharacterController` before parenting and aligning the player. Record whether it was enabled so recovery can restore the expected state.
- Stop active CAS and Tactical weapon use, cancel aim/recoil, and hide or lower both first-person weapon presentations. Do not rely only on blocking future fire callbacks because a held trigger may already be active.
- On exit or recovery, clear all cached passenger/gameplay input again so a key held during touchdown does not leak into the first gameplay frame.

The current prefab also contains presentation components with their own input surfaces. Verify that their `PlayerInput` remains disabled and route weapon visibility/firing through a project-owned integration method or interface. Do not enable or disable the entire Tactical presentation object if doing so would rerun weapon initialization during handoff.

### Passenger look

Store accumulated yaw and pitch as floats in seat-local space; do not clamp world Euler angles.

- Initialize both offsets to zero after the player is aligned to the seat.
- Accumulate input using the same sensitivity/settings source as normal gameplay.
- Clamp to serialized limits, with graybox defaults of approximately `yaw = -75..75` degrees and `pitch = -45..55` degrees. Tune after checking the helicopter interior.
- Build the view from the current seat rotation plus local yaw and pitch every frame. This keeps the bounds stable while the aircraft turns or banks and avoids feedback from the previous camera rotation.
- Apply the view after Timeline has evaluated the helicopter pose for the frame, preferably in `LateUpdate`. Keep the seat hierarchy at unit scale and avoid non-uniform scale above the player.
- Reset offsets during handoff, then initialize normal gameplay aim/body facing from the drop marker's forward direction so the first gameplay frame does not snap back toward the helicopter.

Decide during the graybox pass whether seat roll should be inherited fully or damped for comfort. The bounds must remain seat-local in either case; roll damping is presentation tuning, not a change to the control model.

### `HelicopterInsertionDirector`

Serialized references:

- `PlayableDirector playableDirector`
- `ProjectFPSController playerController`
- `CharacterController characterMotor` if it is not obtained from the controller
- `Transform helicopterSeatAnchor`
- `Transform dropMarker`
- Optional emergency fallback marker; otherwise use the player's valid scene-start pose
- Weapon-presentation integration reference
- A serializable mission-start event or project-owned mission-start channel

Use a small internal state machine such as `NotStarted`, `Playing`, and `Completed`. All normal, skipped, and recovery paths converge on one idempotent method:

```csharp
CompleteInsertion(InsertionCompletionReason reason, bool persistCompletion)
```

Calling completion more than once must be a no-op after the first successful handoff. This protects against a touchdown Signal and `PlayableDirector.stopped` arriving in the same frame.

#### Scene start

1. Cache the player's original parent and valid scene-start pose for emergency recovery.
2. Validate the player, motor, drop marker, seat, director, and playable asset before mutating the player.
3. If the completion flag is set, keep the helicopter inactive, place the player at the drop marker through the shared completion path, and start gameplay without calling `Play()`.
4. If setup is invalid, log each missing reference and use the recovery path. If the drop marker itself is missing, retain the cached valid player pose rather than attempting to teleport to a null target.
5. Otherwise wait until the controller and weapon presentation have completed their normal initialization, then enter passenger mode. A defined script execution order or an explicit initialization-ready property is preferable to assuming arbitrary `Start()` ordering.
6. Activate the helicopter, disable the `CharacterController`, parent the player root to the seat with `worldPositionStays: false`, set local position/rotation to zero/identity, capture the gameplay cursor through the existing UI bridge, and start the Timeline from time zero.

#### Touchdown and skip handoff

Use the same ordered handoff for a Timeline touchdown, a completed-profile skip, and fail-safe recovery:

1. Guard against re-entry and stop/ignore further Timeline callbacks.
2. Stop active firing/aim and clear controller input/state.
3. Keep the motor disabled while changing hierarchy and pose.
4. Unparent the player, then set the root world position and yaw from the drop marker. Do not copy marker scale or pitch/roll to the character root.
5. Verify the target capsule has clearance. The authored marker should be grounded and unobstructed; if a runtime overlap is detected, log it and use the emergency/original pose rather than enabling a controller inside geometry.
6. Reset passenger-look offsets and initialize gameplay-facing state.
7. Re-enable the motor, restore weapon presentation, and enter `Gameplay` mode.
8. Persist completion only after a successful playable handoff. Call `PlayerPrefs.Save()` at this milestone because a crash immediately after landing should not replay the sequence.
9. Emit `MissionStarted` once, after the player is playable.

For a completed-profile skip, mission start still fires once so downstream mission systems do not need separate cinematic and non-cinematic paths.

#### Fail-safe behavior

- Subscribe to `PlayableDirector.stopped`. If it fires before the touchdown handoff, recover into gameplay instead of leaving the player seated.
- Treat a disabled/destroyed insertion component during active play as an interruption and restore player ownership when the scene is still active. Avoid doing scene mutations during application quit or normal scene unload.
- Recovery should not persist completion for an authoring/configuration error; this keeps the problem reproducible after the scene is fixed. A deliberate touchdown or completed-profile skip may persist/retain completion.
- Log the completion reason and recovery destination. Errors should identify the missing reference or interruption rather than only saying the insertion failed.

## Timeline and Scene Authoring

### Graybox helicopter prefab

Create a prefab with:

- A vehicle root animated by Timeline.
- Main-rotor and tail-rotor pivots with independent looping clips.
- A door or ramp pivot and an authored open/close clip.
- A seat anchor positioned at the player's root pose, under only unit-scale transforms.
- Camera-clearance geometry/colliders that do not intersect the allowed look envelope.
- Looping engine/rotor audio sources and optional one-shot touchdown/door sources.

Keep the helicopter root inactive in the authored scene and place the always-active insertion director outside that hierarchy. The director activates the helicopter only after it has checked progress and committed to playback; this prevents a one-frame helicopter flash on completed profiles. The world-space drop marker must remain outside the helicopter hierarchy and active. Never animate the drop marker or the player directly from Timeline.

### Timeline asset

- Animate the helicopter root on an Animation Track using a handcrafted flight clip.
- Use separate tracks for rotors and the door/ramp so their timing can be tuned independently.
- Use Audio Tracks for engine, radio, ambience, and landing cues. Configure spatial blend and loop behavior explicitly.
- Add one touchdown Signal after the aircraft is stationary and the drop area is visually safe. The Signal calls the director's completion entry point; it must not directly manipulate the player.
- Set the `PlayableDirector` update mode to Game Time so the existing `Time.timeScale = 0` pause behavior freezes flight and audio together.
- Set extrapolation/wrap behavior deliberately so an authoring mistake at the end cannot replay the sequence. The stopped callback remains the fallback if the touchdown Signal is missing.
- Bind scene objects explicitly and validate bindings in the director; missing Timeline bindings can otherwise look like a valid director that simply does nothing.

Author the route in three readable beats:

1. **Approach:** establish forward motion and give the player time to inspect the cabin/environment.
2. **Descent:** slow down before aggressive banking near the landing area; open the door/ramp only when camera clipping is safe.
3. **Touchdown:** settle to a fully stationary pose, then fire the touchdown Signal and transition to gameplay.

## Campaign State

Create a small `InsertionProgress` helper rather than scattering raw `PlayerPrefs` calls through scene code.

- Use a versioned, namespaced key such as `projectSapphire.campaign.operationsDemo.helicopterInsertion.v1.completed`.
- `IsComplete` reads the key with a default of `0`.
- `MarkComplete()` sets `1` and saves.
- `ResetCampaignProgress()` deletes only campaign progress owned by this feature and saves; it must not call `PlayerPrefs.DeleteAll()` because that would also erase graphics, audio, HUD, and sensitivity settings.
- Add an Editor menu item under `Tools/FPSProject/Campaign/Reset Helicopter Insertion` with a confirmation and a clear console message.

For this milestone, "fresh campaign" means the insertion key is absent. The current main-menu Operations button only loads `OperationsDemo`; it does not yet distinguish New Campaign from Continue. A future menu change can call `ResetCampaignProgress()` before loading the scene, but that UI work is not required here.

## Implementation Sequence

Treat every lettered sub-step below as one bounded agent run. An agent should implement only the requested sub-step, run its relevant verification, report changed files and remaining risks, and stop without beginning the next sub-step. Complete the sub-steps in order unless the plan explicitly says they are independent.

1. **Establish the project-owned controller seam.**
   - **1A — Add the subclass:** Create the project-owned `ProjectFPSController : FPSExampleController` without passenger behavior. Confirm that it compiles.
   - **1B — Migrate the prefab:** Replace the vendor controller component on `CAS_Player_Example_FPS_Tactical.prefab` with the project-owned subclass, preserve all serialized controller values, and verify that ordinary `OperationsDemo` movement, look, stance, traversal, and weapon behavior remain unchanged.

2. **Implement scripted-passenger behavior before adding Timeline.**
   - **2A — Control state and input policy:** Add `PlayerControlMode`, idempotent entry/exit/recovery APIs, the Look-only passenger allowlist, callback gating, and cached-input/state clearing. Add tests that classify every action in the current Player action map.
   - **2B — Motor and seat attachment:** Gate base per-frame movement/gravity, safely disable and restore the `CharacterController`, parent/align the player to a static test seat, unparent at a test marker, and verify that no movement or seat drift occurs.
   - **2C — Passenger look:** Add seat-local yaw/pitch accumulation, configurable clamps, post-seat-update application, bank/turn tests, and gameplay-facing restoration at handoff.
   - **2D — Weapon integration:** Stop firing/aim/recoil on entry, hide or lower the CAS and Tactical first-person weapon presentations, restore them without reinitialization, and verify that held weapon inputs do not leak across handoff.

3. **Add insertion progress persistence.**
   - **3A — Runtime persistence:** Implement `InsertionProgress` with the versioned namespaced key, `IsComplete`, `MarkComplete()`, and narrowly scoped `ResetCampaignProgress()`. Add persistence tests that confirm settings keys are not erased.
   - **3B — Editor reset command:** Add `Tools/FPSProject/Campaign/Reset Helicopter Insertion` with confirmation and a clear result message. Verify a reset causes the next scene run to take the fresh-profile path.

4. **Implement and verify the director using simple test transforms.**
   - **4A — Core state machine:** Implement validation, initialization readiness, `NotStarted`/`Playing`/`Completed` state, normal start, and the single idempotent completion path without production helicopter or Timeline content.
   - **4B — Normal and skipped handoffs:** Implement touchdown placement, completed-profile skip, progress saving after a successful handoff, and exactly-once `MissionStarted` emission.
   - **4C — Recovery paths:** Implement duplicate-callback protection, stopped-director recovery, missing-reference fallbacks, target-clearance handling, and disable/destroy cleanup.
   - **4D — Director tests:** Cover fresh start, normal touchdown, completed-profile skip, same-frame Signal/stopped callbacks, missing references, interruption, invalid landing clearance, and exactly-once mission start.

5. **Create and connect the graybox sequence in `OperationsDemo`.**
   - **5A — Static scene setup:** Create the graybox helicopter prefab hierarchy, unit-scale seat anchor, world-space drop/emergency markers, and always-active director object. Wire references and verify the static passenger entry and manually triggered handoff before authoring motion.
   - **5B — Flight Timeline:** Create the helicopter route plus separate rotor, door/ramp, engine, radio, and ambience tracks. Configure Game Time update, bindings, and non-looping end behavior without adding the touchdown Signal yet.
   - **5C — Touchdown integration:** Add the touchdown Signal after the stationary landing pose, route it only through the director completion entry point, and verify the full fresh-profile flight hands off exactly once.
   - **5D — Skip and interruption scene pass:** Verify the helicopter never flashes for completed profiles and that stopping the real Timeline before its Signal recovers to a playable world-space pose.

6. **Tune the complete sequence in Play Mode without changing its architecture.**
   - **6A — Camera and comfort:** Tune yaw/pitch limits, inherited or damped roll, flight banking, seat placement, and interior geometry until the allowed look envelope has no camera clipping or uncomfortable motion.
   - **6B — Handoff presentation:** Tune door/ramp timing, weapon lowering/restoration, helicopter stop, drop-marker position/facing, collision clearance, and the first gameplay frame.
   - **6C — Audio and route polish:** Tune route pacing, engine/rotor loops, radio/ambience timing, touchdown cues, and audio continuity across pause and handoff.

7. **Complete final verification.**
   - **7A — Automated suite:** Run all controller, persistence, and director tests. Fix only defects within this feature, rerun until green, and record the results.
   - **7B — Manual acceptance matrix:** Execute every manual case below, record pass/fail evidence and any deferred presentation issue, and stop only when all required acceptance criteria pass or a concrete blocker is documented.

## Test Plan

### Automated controller tests

- Entering passenger mode clears held movement, sprint, crouch, jump, aim, lean, fire, and velocity state.
- Passenger mode accepts Look and rejects every action in the current Player action map. A test fails if an unclassified action is added later.
- Base movement/gravity simulation does not call `CharacterController.Move()` in passenger mode.
- Yaw/pitch clamps remain correct after the seat rotates and banks.
- Exiting passenger mode resets offsets and does not replay input held during the handoff frame.
- Repeated enter/exit/recovery calls leave the controller in one valid state.

### Automated director tests

- Fresh progress starts the director once and does not emit `MissionStarted` early.
- Touchdown unparents and places the player, restores motor/control/weapon state, saves progress, and emits once.
- A second Signal or a same-frame `stopped` callback does not perform a second handoff or event.
- Completed progress skips playback, uses the drop marker, and emits mission start once.
- Missing director, playable asset, seat, player, weapon integration, or drop marker recovers to the best valid pose without throwing or leaving controls disabled.
- Stopping the Timeline before touchdown recovers to gameplay without marking a configuration failure complete.
- Pause/resume preserves director time and passenger mode, then continues from the same point.

### Manual acceptance matrix

- Fresh Editor run after using the reset command.
- Scene reload during the flight.
- Scene reload after touchdown.
- Pause and resume during approach, descent, and immediately before touchdown.
- Hold movement, fire, aim, crouch, jump, reload, switch-weapon, lean, and interact inputs before and across touchdown.
- Mouse and gamepad look at every clamp boundary while the helicopter is level, turning, and banking.
- Temporarily remove the touchdown Signal and stop the director to confirm recovery.
- Temporarily clear each required reference to confirm the logged error and fallback destination.
- Inspect the complete flight for seat drift, camera/weapon clipping, motion discomfort, rotor/door timing, audio discontinuities, landing-marker clearance, and a seamless first gameplay frame.

## Assumptions

- Version one targets only the offline `OperationsDemo` flow. `OperationsDemoMultiplayer` and the network player prefab are unchanged.
- The helicopter route is a handcrafted set piece, not a reusable vehicle or navigation system.
- Mission systems can accept one project-owned `MissionStarted` event after either the Timeline handoff or the completed-profile skip.
- The existing idle/lowered-weapon presentation is acceptable for graybox. A dedicated seated body pose is an art follow-up.
